# 附近频道边界真机验收清单（P2-A）

> 对应 `REWRITE_PLAN_CHECKLIST.md` → P2-A：
> 「附近频道明确 `SocialRoom` 与旧聊天持久化 API 的边界，真机验证不会重复刷屏。」

## 一、边界定义（验收前必读）

附近频道现在有两条链路，**分工不允许混**：

| 链路 | 职责 | 是否写库 | 客户端用途 |
| --- | --- | --- | --- |
| `POST /api/game/chat/nearby`（核心 API） | **持久化唯一入口**，写 `world_local_messages`，返回 `id` + `dedupeKey` | ✅ | 发送后立即合入列表并登记幂等键 |
| `GET /api/game/chat/nearby/sse`（SSE，现役保留） | **持久化回灌唯一通道**（首次历史 + 增量） | ❌（只读） | 消息列表的唯一渲染来源 |
| `SocialRoom` `nearbyMessage` | **只做同图实时广播回声**，携带 `messageId` / `dedupeKey` | ❌ **禁止写库** | 只作为「有新消息」信号，防抖触发一次增量拉取 |

关键约束：

- 房间回声**不直接写入**消息列表，避免与 SSE 回灌重复渲染。
- 房间**不再**通过 `social_event` 广播 `nearby_message`，每条消息只有一帧回声
  （`nearby_chat_echo`），键为 `dedupeKey` > `db:<messageId>` > `room:<roomMessageId>`。
- 成员进出、新消息、重连 replay 必须下发 `progress_refresh`（opcode `12742`，scope `activity`），
  **不允许只回 ACK**。
- 聊天 / 附近频道 SSE 属于现役链路，本轮只做边界收敛，不退役、不删除。

### 进度刷新帧约定

| 场景 | reason | scopes |
| --- | --- | --- |
| 同图有新消息 | `nearby_message` | `["activity"]` |
| 成员加入 / 离开 | `nearby_member_changed` | `["activity"]` |
| 首帧 / 重连 repair | `nearby_replay` | `["activity"]` |
| 核心 API 发送成功 | `nearby_message_sent`（随响应帧组下发） | `["activity"]` |

## 二、前置条件

1. 已部署包含本次改动的前端与 game-server；`NEXT_PUBLIC_GAME_SERVER_WS_URL` 指向可达的 game-server。
2. 准备 **两个已登录账号 A / B**，两者当前所在地图相同（同 `mapId`、同 `shardId`）。
3. 准备第三个账号 C，用于成员进出验收。
4. 移动端请把浏览器控制台打开（iOS Safari 可用 Mac Safari 远程调试；Android Chrome 用 `chrome://inspect`），
   便于观察 `nearby_chat_echo` 与 `progress_refresh` 帧。
5. 记录基线：进入聊天页 → 「附近」页签，顶部标签应能看到
   `消息 N`、`同图 M`（M ≥ 2 说明 A、B 在同一 SocialRoom），以及 `动态 K`（收到过 `activity` 进度帧后 > 0）。

## 三、验收项

### A. 一条附近消息只渲染一次（不重复刷屏）

**步骤**

1. A、B 同时停在聊天页「附近」页签，保持页面前台。
2. A 发送一条消息，例如「重复刷屏验收 01」。
3. 观察 B 的列表（A 自己的列表同样适用）。

**预期**

- B 的列表中该消息**只出现 1 条**，不出现两条内容相同的消息。
- 顶部 `消息 N` 只 +1。
- 列表不发生闪烁 / 跳变 / 被整体重建（没有短暂清空再重灌）。
- 控制台不应出现同一条消息被渲染两次的迹象（例如同一 `dedupeKey` 对应两条 DOM 节点）。

### B. 持久化 API 与房间广播不产生重复

**步骤**

1. A 连续发送 3 条不同内容消息（间隔 1 秒左右），B 保持观察。
2. A 再快速连点发送按钮 2 次（模拟弱网重试 / 手抖）。

**预期**

- 3 条不同消息各渲染 1 条，顺序按消息 id 升序，无重复。
- 快速连点**同一条**内容若带同一 `clientMessageId`，服务端命中幂等键只入库一次
  （响应 `dedupeHit: true`），列表不出现重复。
- 同图 N 条回声只触发**一次**增量拉取（防抖 250ms），网络面板里不会出现 N 个
  `GET /api/game/chat/nearby` 请求尖峰。

### C. 弱网 / SSE 断开后房间回声降级仍不重复

**步骤**

1. B 打开飞行模式 5 秒后关闭（或用 DevTools 断网 5 秒），期间 A 发送 2 条消息。
2. B 网络恢复，等待 SSE 自动重连（约 2 秒重试）。

**预期**

- B 恢复后列表中这 2 条消息各只出现 1 条，不会因为「SSE 重连回灌 + 房间回声补拉」出现两条。
- 未出现消息乱序（仍按 id 升序）。

### D. 切换地图后频道正确

**步骤**

1. A、B 都在地图 X，各自发 1 条消息，确认互相可见。
2. A 通过地图移动到地图 Y，再从地图入口进入聊天页「附近」页签。
3. A 在地图 Y 发 1 条消息；随后回到地图 X，再发 1 条消息。

**预期**

- A 在地图 Y 时，列表**只显示地图 Y 的消息**，顶部地图名标签切换为 Y；
  切图瞬间列表被清空并只灌入 Y 的历史（不会残留 X 的消息）。
- B（仍在 X）**看不到** A 在 Y 发的消息。
- A 回到 X 后，列表重新显示 X 的消息，A 在 Y 发的消息不出现在 X 列表里。
- 街区视角 / 全图视角切换时，列表同样清空重建一次，不混显两种范围。

### E. 锁屏回来不刷历史

**步骤**

1. B 停在「附近」页签，记录当前列表最上面一条消息与 `消息 N` 数值。
2. 锁屏（移动端）或切到其它 App / 其它标签页 60 秒以上。
3. 解锁回到页面（触发 `visibilitychange` / `pageshow`）。

**预期**

- 列表**不会整段重灌**：已有消息不重复追加，`消息 N` 数值不异常跳增。
- 如果期间有新消息，只追加增量部分，且每条只出现一次。
- 滚动位置保持在底部附近，不会因重灌被强制拉回顶部。
- 调试观察：恢复后可能收到**两条** `progress_refresh`(12742)，一条是 repair 补齐通道的
  `repair:<trigger>:<reason>`，一条是附近频道的 `nearby_replay`。这是预期的——
  附近频道只消费后者（客户端按 reason 白名单过滤），因此**只会触发一次增量拉取**。
  若观察到 `消息 N` 一次恢复涨了 2 以上，或出现两次网络拉取，即为不合格。

### F. 成员进出与进度刷新帧

**步骤**

1. B 停在「附近」页签，观察顶部 `同图 M` 与 `动态 K`。
2. C 进入同一地图并打开聊天页「附近」页签；等待 3 秒。
3. C 关闭页面 / 退出登录；等待 3 秒。

**预期**

- C 加入后，B 的 `同图 M` 数值 +1；C 离开后 -1。
- 每次成员变化 B 都会收到 `social_event`（opcode `10202`，`presence_join` / `presence_leave`）
  **并且**随后收到 `progress_refresh`（opcode `12742`，`scopes` 含 `activity`，
  reason `nearby_member_changed`）；`动态 K` 数值递增。
- 不会出现只回 ACK、没有进度帧导致 `同图 M` 长期停在旧值的情况。
- 成员变化**不会**伪造背包 / 资产刷新帧（`inventory_refresh` 10302 / `asset_refresh` 10510 不应出现）。

### G. 房间重连后 replay 不重复

**步骤**

1. B 停在「附近」页签，记录 `消息 N`。
2. 断网 10 秒后恢复（触发 Colyseus 重连 + 客户端 `repair`）。

**预期**

- 恢复后 B 收到 `progress_refresh`（`12742`，reason `nearby_replay`，scope `activity`）。
- 只做**一次**增量同步，不把历史整段重灌：`消息 N` 不异常跳增，已有消息不重复。
- 断网期间他人发送的消息在恢复后各只追加 1 条。

### H. 三端一致性

在以下三种环境各跑一遍 A / D / E / F：

- iOS Safari（iPhone 真机，含锁屏场景）
- Android Chrome（真机，含锁屏 / 切后台场景）
- PC 浏览器（Chrome 桌面版，窗口尺寸拉窄到 390×844 模拟竖屏）

**预期**

- 三端表现一致：不重复刷屏、切图频道正确、锁屏回来不刷历史、成员变化有进度帧。
- 竖屏下「附近」页签顶部标签不遮挡消息列表；消息列表区域仍是页面主体。
- PC 上不应出现把消息区压到左侧的横屏仪表盘布局。

## 五、已知风险与遗留项

1. **幂等键只对带 `clientMessageId` 的发送生效**。NPC / 天道系统消息不携带幂等键，
   仍靠消息 `id` 去重；若将来系统消息改成高频生成，需要补幂等键。
2. **内存兜底模式**（`storageMode: "memory"`）下消息 id 是进程内自增，
   多实例部署时不同实例 id 会冲突；该模式仅用于 DB 不可用降级，正常链路走 Postgres。
3. **同图人数很多时**，成员进出会对每个同图玩家各下发一帧 `progress_refresh`，
   是 O(n) 次投递；当前同图规模可接受，若后续出现百人同图需改为批量帧。
4. **历史数据没有 `dedupe_key`**（NULL 不参与唯一冲突），老消息仍只按 `id` 去重，行为不变。
5. 房间回声不落库，若 SSE 长时间不可用且核心 API 也不可用，房间内消息只有回声提示、
   无法补齐内容 —— 这是刻意的边界（房间不伪造持久化），此时应表现为「列表短暂缺失、
   恢复后按 id 补齐」而不是出现重复。
